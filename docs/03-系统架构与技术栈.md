# 系统架构与技术栈

## 1. 架构选择

首期采用“模块化单体 API + 异步 Worker + 专用解析/推理容器”。这能保留清晰模块边界，同时避免在业务尚未稳定时引入微服务治理成本。

```text
浏览器
  │
  ▼
Next.js Web ───── FastAPI
                    │
          PostgreSQL│Redis
                    │
                    ▼
              Celery Worker
          ┌─────────┼──────────┐
          ▼         ▼          ▼
       GROBID    R Worker   Model Worker
          │         │          │
          └─────────┼──────────┘
                    ▼
            任务级 MinIO 空间
                    │
                    ▼
             FAISS 临时索引
```

## 2. 技术栈

### 用户界面

- Next.js + TypeScript：任务、证据和报告界面。
- PDF.js：显示待检与对照 PDF。
- Canvas/SVG overlay：按真实 PDF 坐标叠加文本片段、图像区域和连线。
- UI 组件库在实现时只选一套；优先满足双栏证据审查、键盘导航和长文档性能。

### API 与业务层

- Python + FastAPI + Pydantic。
- SQLAlchemy + Alembic管理 PostgreSQL 模型与迁移。
- OpenAPI作为前后端接口契约。
- httpx用于外部学术 API 和全文下载；重试必须尊重 `Retry-After`，不伪造成功。

### 异步任务

- Celery + Redis。
- 每个检查任务有明确阶段和幂等键；相同引用下载、解析和检测不得重复并发执行。
- Worker只产生检测事实和证据，不直接写最终人工裁决。

### 文件与临时索引

- PostgreSQL存储任务状态、书目元数据、证据索引、裁决和审计事件。
- MinIO/S3兼容存储保存源文件、引用全文、TEI、图片、临时索引和最终报告。
- FAISS为每个任务建立独立本地向量索引；索引文件属于临时任务资产。
- 首期不引入 OpenSearch、Qdrant、Kafka 或 Kubernetes。

### 文档处理

- GROBID：学术 PDF 到 TEI XML。
- PyMuPDF：页级渲染、坐标转换、嵌入图片和区域提取。
- PaddleOCR：仅对没有可靠文本层的扫描页启用。
- DOCX 与 LaTeX 支持可以在 PDF 主链稳定后补充，最终都要归一为相同文档结构。

### 文本检查

- Unicode、空白、断词和参考文献规范化保留原文映射，不能破坏证据定位。
- Winnowing/MinHash生成词面候选。
- BGE-M3 + sentence-transformers生成多语言段落向量。
- FAISS执行任务内候选召回。
- Cross-Encoder对候选重排。
- RapidFuzz及字符/词级局部对齐确定最终片段边界。

向量相似度只参与召回和排序；证据必须以可查看的原文片段与精确位置呈现。

### 引文论断核验

- 规则与 GROBID 先建立“正文论断—引用标记—参考文献”关系。
- 从被引全文检索相关段落。
- 本地模型将关系分类为支持、部分支持、相反、未找到证据或全文不可获得。
- 模型推理通过 PyTorch/Transformers；并发扩大后可用 vLLM。
- 任何分类必须携带被引原文，不能只保存模型解释。

### 统计与数据检查

- R Worker：statcheck、scrutiny、rsprite2。
- Python：Polars/pandas、NumPy、SciPy、statsmodels。
- Python与R之间使用版本化 JSON/CSV 契约；R包输出统一转换为 `EvidenceItem`。
- 首期不执行用户提供的分析代码；数据文件只作为数据读取和受控复算输入。

### 图片检查

- PyMuPDF提取 PDF 嵌入图片及页面渲染图。
- OpenCV执行面板切分、局部特征、几何验证和 copy-move 辅助分析。
- Pillow/imagehash提供基础感知哈希。
- SSCD负责对裁剪、压缩和视觉变化更稳健的候选召回。
- 候选必须通过局部匹配、几何关系和人工查看确认。

### 报告与观测

- Jinja2生成可版本化 HTML。
- WeasyPrint生成 PDF 报告。
- OpenTelemetry贯穿 API、任务和检测器。
- Prometheus/Grafana观察吞吐与资源；Sentry或等价系统收集经过脱敏的应用错误。

## 3. 建议代码结构

```text
SBDC/
├── apps/
│   ├── web/
│   ├── api/
│   └── worker/
├── packages/
│   ├── domain/
│   ├── document_parser/
│   ├── reference_resolver/
│   ├── source_fetcher/
│   ├── text_forensics/
│   ├── citation_checker/
│   ├── statistics_forensics/
│   ├── image_forensics/
│   ├── evidence/
│   └── reporting/
├── services/
│   ├── grobid/
│   ├── r-worker/
│   └── model-worker/
├── migrations/
├── tests/
│   ├── fixtures/
│   ├── goldens/
│   ├── integration/
│   └── e2e/
├── docs/
└── compose.yaml
```

`packages/domain`定义唯一业务状态与证据契约；各检测器通过端口接口接入，避免把开源项目的数据结构暴露到产品界面。

## 4. 扩展条件

只有出现明确证据才升级基础设施：

- 单任务语料或并发使 FAISS 文件无法在合理资源内处理时，再评估 Qdrant。
- 出现跨任务、长期合法语料检索需求时，必须先形成新的产品与版权决策，才能评估 OpenSearch。
- 单机 Worker已成为经测量的吞吐或隔离瓶颈时，再评估 Kubernetes。
- 不能因“以后可能需要”提前引入这些组件。
