# 数据模型与任务生命周期

## 1. 核心对象

### PaperTask

表示一次独立检查，不表示长期论文资产。

关键字段：

- `id`
- `status`
- `evidence_level`：`L1`、`L2`、`L3`
- `requested_checks`
- `source_file_id`
- `retention_policy`
- `coverage_summary`
- `created_at`、`completed_at`

### DocumentAsset

表示源论文、引用全文、原始数据、原图或派生产物。

关键字段：

- `id`、`task_id`
- `role`
- `storage_key`
- `sha256`
- `media_type`、`size_bytes`
- `license_status`
- `provenance`
- `retention_state`

### ReferenceSource

表示待检论文的一条规范化引用。

关键字段：

- `id`、`task_id`
- 原始引用文本
- DOI或其他标识
- 规范化题名、作者、年份、来源
- 解析置信度
- 全文获取状态及来源
- 撤稿/更正状态
- 对应 `DocumentAsset`

### CitationContext

连接正文论断、引用标记和 `ReferenceSource`，同时保留页码、字符偏移和 PDF 坐标。

### EvidenceItem

所有检测器的统一输出。

```json
{
  "id": "evidence-id",
  "task_id": "task-id",
  "category": "text_reuse",
  "status": "needs_review",
  "severity": "high",
  "confidence": 0.91,
  "subject_location": {
    "document_id": "source-paper",
    "page": 27,
    "char_start": 1024,
    "char_end": 1310,
    "bbox": [72.1, 122.4, 514.8, 301.2]
  },
  "source_location": {
    "reference_id": "reference-id",
    "page": 8,
    "char_start": 520,
    "char_end": 801
  },
  "subject_excerpt": "待检论文原文",
  "source_excerpt": "对照来源原文",
  "method": {
    "detector": "text-alignment",
    "version": "pinned-version",
    "parameters": {}
  },
  "limitations": ["仅在已取得的引用全文范围内检查"],
  "artifacts": [],
  "created_at": "ISO-8601"
}
```

`confidence`是该检测器对匹配或不一致的置信度，不是论文存在学术不端的概率。

### ReviewDecision

人工对一项证据作出的决定：确认异常、要求补充、证据不足或合理复用。它保存审查人、时间、理由和证据版本，不能覆盖原始检测输出。

### AuditEvent

记录材料接收、引用获取、模型/规则执行、报告生成、保留选择和清理结果。审计日志不保存不必要的正文片段或敏感数据。

## 2. 任务状态机

```text
created
  → validating
  → parsing
  → references_ready
  → fetching_sources
  → indexing
  → checking
  → review_ready
  → reviewed
  → reporting
  → completed
  → retention_pending
  → retained | purged | purge_failed
```

失败是附着在具体阶段上的可恢复状态，不能用一个模糊的 `failed` 丢失事实。取消操作保留已产生的审计证据，并进入同样的资产处置流程。

## 3. 覆盖率契约

`coverage_summary`至少包含：

- 识别出的引用总数；
- 成功规范化数；
- 可合法获得全文数；
- 成功解析数；
- 实际进入文本、引文和图片检查的数量；
- 每个检测器的适用项、成功项、跳过项和失败项；
- 原始数据与原图是否存在。

报告结论必须从覆盖率生成，不能使用笼统的“已全面检查”。

## 4. 任务级存储布局

```text
tasks/{task_id}/
├── source/
├── references/
├── parsed/
├── datasets/
├── images/
├── indexes/
├── evidence/
└── reports/
```

所有对象键都由系统生成的任务和资产 ID 构造，不使用用户文件名拼接路径。临时索引不得引用其他任务目录。

## 5. 保留与清理

创建任务时向用户说明可选策略：

- 检查完成后清理临时全文与派生产物；
- 在指定期限内保留以便复核；
- 经授权保留完整案件包。

清理后可以保留最小审计信息：书目元数据、获取状态、文件不可逆摘要、证据记录、人工决定和清理事件。是否保留命中原文片段由案件策略和权限决定。

清理采用明确对象清单和幂等操作；只有所有目标对象均回读为不存在或已达到规定保留状态，任务才进入 `purged`。清理失败进入 `purge_failed` 并可安全重试。

## 6. API 边界草案

- `POST /tasks`：创建任务并声明证据等级与保留策略。
- `POST /tasks/{id}/assets`：上传源论文或补充材料。
- `POST /tasks/{id}/parse`：开始解析。
- `GET /tasks/{id}/references`：查看并确认引用清单。
- `POST /tasks/{id}/checks`：开始已选择的检查。
- `GET /tasks/{id}/coverage`：获取实时覆盖范围。
- `GET /tasks/{id}/evidence`：分页获取证据卡。
- `POST /evidence/{id}/decisions`：提交人工裁决。
- `POST /tasks/{id}/reports`：生成指定证据版本的报告。
- `POST /tasks/{id}/retention`：确认保留或清理策略。

这些路径是实现草案，不是已经存在的接口。实现时先用 OpenAPI和领域状态机锁定请求、响应、幂等和权限语义。
